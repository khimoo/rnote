# PDF のページを参照で取り込む機能の設計

- 日付: 2026-09-28
- 基準にした本家のコミット: flxzt/rnote `29ea24a1`（2026-09-25）
- 状態: 実装済み。UI での手動確認はまだ

## 目的

教科書の PDF（数百ページ、スキャンと電子版の両方）の全ページを、無限キャンバスに格子状に並べ、液タブで書き込みながら勉強する。

成功の条件は次のとおり。

- 全ページを取り込んだあとに残るメモリが、ページ数によらず PDF 本体の大きさ程度に収まる
- 縮小して全ページを見渡したとき、描画に使うメモリが 150 MB 以内に収まる
- 拡大と縮小を繰り返しても、ページ画像のキャッシュが上限を超えない
- 拡大しても、電子版の文字がぼやけない

## 前提

- 使うマシンはノート（4 スレッド、7.6 GiB）とデスクトップの 2 台で、メモリの予算はノートに合わせる。どちらも GNOME 49 の Wayland で UGEE の液タブを使う。
- 本家には PR を出さない。rebase の衝突は小さく保つが、hayro は本家より新しい版に上げる（描画の質を優先するという利用者の判断）。
- 文書のレイアウトは「無限」で使う。
- PDF は外部ファイルとして参照する。2 台で使うときは、どちらのマシンでも同じ絶対パスに置く。

## 本家の現状

本家の PDF 取り込みには、ビットマップとベクターの 2 方式がある。
どちらも取り込み時に全ページを変換し、変換結果を要素として持ち続ける。
ビットマップ方式は固定の解像度で描いた RGBA の画素を、ベクター方式はページごとの SVG の文字列を持つ。

本家で進行中の関連 PR と issue は次のとおり。

- #1743: 取り込み設定に列数を足し、ビットマップとベクターの取り込み処理のそれぞれに列の配置を書いている（未マージ）
- #1854: 取り込み時のメモリのピークを下げる（未マージ）。作者は、取り込み後に残るメモリには手を付けないと明記している。400 ppi のスキャンで 204 ページの教科書を全部取り込むと、約 1.2 GB が残る
- #1578: 新しい保存形式（未マージ）
- #459: 拡大縮小を繰り返すとメモリが数 GB に増える（未解決）

描画する側は、すでに表示範囲に応じて描き直す仕組みを持っている（`store/render_comp.rs` の `regenerate_rendering_in_viewport_threaded`）。
表示範囲を少し広げた範囲から外れた要素は描画結果が捨てられ、表示範囲やズームが変わると描き直される。
この機能では、PDF を保持したまま、表示範囲にあるページだけを必要な解像度で描く要素を新しく足す。

## PdfSource

1 つの PDF につき、プロセス全体で 1 つだけ作る。
登録表は、正規化した絶対パスをキーに `Weak<PdfSource>` を引く表で、`Mutex` で守る。
そのため、300 ページぶんの要素が同じ `PdfSource` を共有する。
どの要素からも参照されなくなると解放される。

中身は次のとおり。

- PDF のバイト列（`Arc`）と、hayro で解析した `Pdf`
- ハッシュ（CRC32 とバイト長）
- ページごとの寸法
- ページ画像のキャッシュ

PDF を開くのは、取り込むときか、そのページが最初に描かれるときだ。
開く処理は、描画を担当する rayon のスレッドの上で同期的に行う。

ページ画像のキャッシュのキーは、ページ番号と段 `k` の組だ。
段 `k` の画像は、PDF の 1 ポイントあたり `2^k` 画素で描く。
文書の単位ではなくポイントを基準にするので、同じページを別の大きさで置いた要素どうしでもキャッシュを共有できる。
上限はバイト数で決める（初期値 512 MB）。
上限を超えたら、最も長く使われていないものから捨てる。
上限より大きい画像 1 枚は、キャッシュに入れない。

Rnote は要素ごとに rayon のスレッドで描くので、`PdfSource` は `Send + Sync` でなければならない。
hayro-syntax の `Pdf` は、`std` 機能（既定で有効）のもとでは内部に `std::sync::Arc` を使う。
hayro の `RenderCache` は内部に `Rc` と `RefCell` を持ち、スレッド間で共有できない。
そのため `RenderCache` は描画 1 回ごとに作り、描画をまたいで使い回すのは上のページ画像のキャッシュだけにする。

## PdfPage 要素

保存するフィールド（serde 名は `pdfpage`）:

- `pdf_path`: PDF の絶対パス
- `pdf_hash`: CRC32 とバイト長
- `page_index`: 0 から数えたページ番号
- `rectangle`: 位置、大きさ、変形。既存の画像要素と同じ `Rectangle` を使う

保存しないフィールド:

- 解決済みの `PdfSource` への参照。初めて使うときに登録表から引く。失敗も記録しておき、ファイルを毎回開き直すことはしない。文書を開き直したときに再び試す

各 trait の実装は次のとおり。

- `Content::gen_images`: 次の「描画」の節で説明する
- `Content::gen_svg`: hayro-svg でページを SVG にし、`rectangle` の変形を付けて返す。PDF や SVG に書き出すときに使われる
- `Content::draw_highlight`、`Content::update_geometry`: 既定の実装を使う
- `Drawable::draw`: ページ全体を `image_scale` で描いて貼る。上限は「描画」の節の全体モードと同じにする。`gen_images` を通らない経路（選択範囲のプレビューや書き出し）で使われる
- `Shapeable`、`Transformable`: 既存の画像要素と同じく `rectangle` に任せる
- `Stroke` のその他のメソッド: 色の反転などは何もせず `false` を返す。Xournal++ 形式への書き出し（`into_xopp`）では `None` を返して省く。既定のレイヤーは `Document` にする

## 描画

`gen_images(viewport, image_scale)` は次の手順で描く。
`viewport` は文書の座標で表した表示範囲（少し広げたもの）、`image_scale` は文書の単位 1 あたりの画素数だ。

1. `R` を `viewport` とページの外接矩形の共通部分とする。空なら、空の `Partial` を返す。
2. `PdfSource` を引く。PDF が見つからない、読めない、ハッシュが合わない、解析に失敗したといった場合は、灰色の矩形を描き、理由をログに出す（1 つの PDF につき 1 回）。
3. 必要な解像度 `s`（PDF の 1 ポイントあたりの画素数）を、`image_scale` と「要素の大きさ ÷ ページの大きさ（ポイント）」の積として求める。段 `k = ceil(log2(s))` でページ全体を描いたときの長辺が 4096 画素以下なら全体モード、超えるなら部分モードにする。
   - 全体モード: キャッシュから段 `k` のページ画像を取る。なければ `hayro::render` で描いてキャッシュに入れる。取った画像に要素の `rectangle` を付けて、そのまま `Full` として返す。Rnote は画像を `rectangle` の変形付きのテクスチャとして描くので、回転した要素にも合成し直さずに使える。画像の画素は `glib::Bytes` で共有されるので、キャッシュとの間で複製は起きない。
   - 部分モード: `R` の大きさに `image_scale` を掛けた大きさのバッファに、`hayro::render_into` でページを描く。変換には、ページの座標から文書の座標への変換（`rectangle` の変形）に、文書の座標からバッファへの変換（`R` の左上を原点に移し、`image_scale` 倍する）を合成したものを使う。結果はキャッシュしない。

縮小して全体を見渡すときは小さな段で足りる。
長辺 256 画素なら 1 ページ約 0.19 MB で、300 ページでも約 55 MB で済む。

スキャンしたページは、描くたびに埋め込み画像の全体が元の解像度で展開される（#1854 の計測では 4676×3306 の画像で 1 回 46 MB）。
同時に展開されるのは rayon のスレッド数ぶんまでで、全体モードでキャッシュに当たれば展開は起きない。

## 取り込み

アプリのメニューに「Import PDF as Page References…」を足す（UI の文字列は英語で、翻訳は付けない）。

1. `gtk::FileDialog` で PDF を選ぶ
2. エンジン側で PDF を開き、ページ数を読む。パスワードが必要な PDF はここでエラーにする。描くたびに PDF を開き直す設計なので、扱うにはパスワードを保存しなければならなくなるからだ
3. ダイアログで、ページ範囲（既定は全ページ）、列数（1〜64、既定は 8）、ページの間隔（列の幅に対する割合で 0〜200%、既定は 10%）を指定する
4. エンジンが要素を作り、既存の `import_generated_content(strokes, false)` に渡す。取り込んだページは文書レイヤーに入る。取り込み直後は全ページが選択され、1 回の取り消しで全体を戻せる

配置の規則は次のとおり。

- 倍率は、最初のページの幅が文書の用紙幅になるように決め、全ページに同じ倍率を掛ける（既存の取り込みと同じ）
- 列の幅は全ページの最大幅、行の高さはその行でいちばん高いページの高さにそろえる
- 置く位置は既存の取り込みの既定位置と同じにする。その位置を求める関数（`canvas/imexport.rs` の `determine_stroke_import_pos`）は非公開なので、同じ計算をダイアログ側に書く

取り込むときには描画しない。
PDF を開いてページの寸法を読むだけなので、ページ数が増えても時間はほとんど変わらない。

## hayro の更新

ワークスペースの `hayro` と `hayro-svg` を、hayro の main の `ae09437`（2026-09-26）に固定する。
この版は Rust 1.92 以上を要求する。
既存のコードは次のように合わせる。

- `render` と `convert` の引数に `RenderCache` を足す
- `RenderSettings` から `width` と `height` がなくなった。既存のビットマップ取り込みはこの 2 つを明示していたので、倍率から決まる大きさに任せる。端数の丸め方が違うので、1 画素ずれる場合がある

## ビルドと flake

- `flake.nix` の入力は nixos-unstable にする（デスクトップの nixpkgs の rustc は 1.91.1 で、1.92 に足りない）
- 出力は `packages.x86_64-linux.default`（nixpkgs の rnote と同じく meson と cargo でビルドし、依存は `rustPlatform.fetchCargoVendor` のハッシュ 1 つで固定する）と、開発用の `devShells.x86_64-linux.default`
- flake_public からは `github:khimoo/rnote` として取り込み、`packages.${system}.default` を使う
- ビルドとテストはデスクトップの `/tmp` に作業ツリーを複製して行う

## テスト

`rnote-engine` の単体テスト:

- 格子の配置の計算
- 段の求め方と、全体モードと部分モードの切り替え
- キャッシュがバイト数の上限で捨てられること
- 保存と読み込みで要素の内容が変わらないこと
- 同じ PDF の要素が `PdfSource` を 1 つだけ共有すること
- 部分モードで、表示範囲と重なる部分だけが描かれること
- PDF がない場合とハッシュが合わない場合に灰色の矩形になること

テスト用の PDF は 2 種類作り、リポジトリに入れる。
1 つは Typst で作る複数ページのベクター PDF、もう 1 つは画像だけのページからなるスキャン相当の PDF だ。

性能は、メモリの確保を数える計測用の example で確かめる。
300 ページ相当の PDF を取り込み、縮小して全ページのサムネイルを描き、拡大と縮小を往復させて、ピークと取り込み後に残るメモリを測る。
目標は「目的」の節の成功の条件と同じ。

最後に、2 台の液タブで実際の教科書を使い、書き心地を確かめる（利用者が行う）。

## 計測結果

2026-09-29 に、`crates/rnote-engine/examples/pdfpage_bench.rs` で計測した。
対象の PDF は `pdfpage_bench.typ` から作った 300 ページの PDF（0.2 MB）で、各ページに 1240×1754 の JPEG を 1 枚ずつ貼っている（A4 を 150 dpi でスキャンしたものに相当）。
マシンはデスクトップで、計測は 1 スレッド、cargo の dev プロファイル（`opt-level = 2`）で実行した。
メモリは Rust のアロケータで確保した量で、GTK が作るテクスチャは含まない。

- 取り込み後に残るメモリ: 1.0 MiB（0.00 秒）
- 8 列の格子を幅 1920 画素に縮小して全ページを描き、全部の画像を保持したとき: 143.9 MiB、ピーク 145.8 MiB（2.34 秒）
- 最初の 16 ページについて、縮小表示から 2048 倍まで拡大して戻す操作を 3 往復したあと: 184.0 MiB、ピーク 194.5 MiB（0.54 秒）。このうち 182.9 MiB がページ画像のキャッシュ
- 要素と `PdfSource` を捨てたあと: 0.0 MiB
- 比較として、同じ PDF を本家のビットマップ方式（既定の設定）で取り込んだ場合: 残るメモリ 1652.0 MiB、ピーク 1785.6 MiB（10.90 秒）

「目的」の節の成功の条件は、いずれも満たしている。
全体表示の 143.9 MiB は、段を 2 の累乗に切り上げていることによる。
画面上ではページの幅が約 220 画素のところを、段 −1（0.5 画素/ポイント、297×420 画素）で描いている。
段を細かくすればこの値は下がるが、条件を満たしているので上限の値（全体モード 4096 画素、キャッシュ 512 MB）は変えない。

スキャンの解像度が高い教科書（例えば 400 ppi）では、1 ページを描くたびに展開する画像が約 7 倍大きくなるので、最初に全体を表示するときの時間はその分延びる。
ノート（4 スレッド）での時間は計測していない。

- 実際の教科書（高解像度のスキャン、日本語の電子版）で、描画の時間とフォントの表示が問題ないか
